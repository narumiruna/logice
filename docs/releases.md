# Releases

Logice uses Changesets 3 to collect release notes and update the application version. Release tooling stays in `web/`; Go checks do not need Node.js or a root npm package.

## Release scope

- `web/package.json` is the application version source. It stays private.
- `web/CHANGELOG.md` contains the release notes generated by Changesets.
- Git tags and GitHub source releases use `v<version>`, such as `v0.1.0`.
- The first pending changeset selects `0.1.0` from the initial `0.0.0` metadata version.
- Helm chart versions stay separate. This workflow does not edit chart defaults or deploy services.
- No npm package or release binary is published. GitHub provides its standard source archives.
- `.github/workflows/docker.yml` still publishes commit-tagged images and `latest` on `main`. It does not add version image tags. Pin API and web images to the commit referenced by the release tag, not to `v<version>`.

## Add a changeset

Use Node.js 26.11.1 and npm 11.20.0. From the repository root:

```sh
npm --prefix web ci
npm --prefix web run changeset -- add --patch logice-web --message "Fix the stated behavior."
```

Use `--minor logice-web` for a feature or `--major logice-web` for a breaking change. Commit the new Markdown file under `web/.changeset/` with the code. Do not include credentials or private telemetry in release notes. A change with no release impact does not need a changeset.

## GitHub workflow

`.github/workflows/release.yml` runs on pushes to `main`. Manual runs also require `main`. It uses one concurrency group, does not cancel an active release, and has a 15-minute job deadline. It checks Go and the frontend before it can write release metadata.

1. When pending changesets exist, the pinned Changesets action opens or updates `changeset-release/main`. New version PRs are drafts. It updates the private package version, npm lockfile, and changelog, then removes the consumed changesets.
2. Review the version PR and its notes. Complete the required checks and applicable operator release gates. The generated Changesets PR text can refer to npm; this repository does not publish to npm.
3. Merge the approved version PR. With no pending changesets, the workflow creates the annotated version tag and pushes it through the GitHub API. It then creates a GitHub release from the changelog stored at that tag.
4. A normal push with an already released version does not replace its tag or release notes.

The job needs `contents: write` and `pull-requests: write`. Other jobs and workflows keep their existing permissions. In repository settings, enable **Actions → General → Allow GitHub Actions to create and approve pull requests**. No npm token, extra GitHub token, or production credential is needed.

A PR created with `GITHUB_TOKEN` does not start another workflow automatically. Run CI on the version branch before merge:

```sh
gh workflow run ci.yml --ref changeset-release/main
```

Check the run on the exact version PR head. Do not bypass required checks or approve a release only because version generation passed. Physical-authenticator validation, database/key backup, and other documented production gates remain operator tasks.

## Local checks

```sh
npm --prefix web run changeset -- status
npm --prefix web run test:release
npm --prefix web run ci
actionlint .github/workflows/release.yml
```

The release tests use a disposable local Git repository and mocked GitHub commands. They check private-package versioning, lockfile updates, changelog generation, tag creation, repeat runs, API denial, tag/version mismatch, and recovery after a failed GitHub release. They do not push tags or create GitHub releases.

## Recovery

The workflow rejects the initial `0.0.0`, prerelease versions, public-package metadata, and versions without release notes. Only stable releases are supported.

If version PR creation fails, check the Actions PR permission and branch rules, then rerun the failed workflow. If tag creation or push fails, check repository access and tag rules. Do not force-push or move a published tag.

If the tag push passed but GitHub release creation failed, rerun the workflow on `main`. Existing tags are not recreated. Release notes are read from the tag, not from later source changes. An existing GitHub release is left unchanged. API errors other than a missing release stop the workflow; they are not treated as permission to create another release.

To stop release automation, disable the Release workflow or revert its configuration. Keep existing tags and releases. Correct a published version with a new changeset and a new version; do not silently replace published source. No live release or deployment was run while adding this workflow.
